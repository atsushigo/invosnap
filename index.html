這是什麼

店長每天要處理最多 5 家供應商、每家約 3 張 A4 紙本進貨單（品項、單價、重量/數量，各家單位不一）。現況是手動把這些資料一筆一筆 key 進 POS 系統，費時又容易出錯，且總部 POS 暫無資源開發此功能。

InvoSnap 是一個獨立於總部 POS 之外的輔助小工具：手機拍照 → 影像辨識抽取結構化資料 → 依供應商對照表換算成店內統一單位/格式 → 產出可匯入（或未來可API串接）POS的進出貨資料。

01 · 專案範疇與痛點

問題定義、使用者、目標、非目標、風險

背景

  • 使用者是川醉湘（麻辣烫/滷味連鎖）某台灣分店的店長。
  • 總部POS系統功能有限，且總部目前沒有資源為單一分店客製開發新功能。
  • 店長希望先有一個「店內自建的輔助工具」，不依賴總部排期。

現況痛點

每天最多約 5 家供應商送原料，每家供應商一天約開出 3 張紙本進貨單（尖峰情境下單日最多約15張紙本單據）。

單據格式：類似A4大小、每家供應商「自己固定」的版式（非全店統一格式），內容包含：

  • 供應商/廠商別
  • 品項名稱（如：青江菜、小白菜…）
  • 單價
  • 數量／重量（單位依供應商不同：台斤、公斤…）

目前作法：店長手動把紙本資料一筆筆輸入POS，耗時、易誤植（尤其單位換算容易出錯）。目標是把這些單據轉換成「店內系統統一單位、統一格式」的進出貨資料，最終寫入（或匯入）POS。

使用者與角色

角色說明
店長（主要使用者）每日收貨時用手機拍照上傳單據、覆核辨識結果、確認入帳
（未來）加盟業主/總部若擴散到其他分店，可能需要多店/多帳號管理
供應商被動角色，不使用系統，只是單據格式的來源（每家格式可能不同、也可能不時微調）

目標（Goals）

  1. 用手機拍照取代手動輸入，減少每日鍵入紙本資料的時間。
  2. 自動辨識供應商別、品項、單價、數量/重量，並依供應商對照表換算為店內統一單位。
  3. 產出可匯入POS（或未來可API串接）的進出貨資料。
  4. 保留「人工覆核/修正」步驟，辨識結果不強制自動入帳，降低誤判風險（尤其金額類資料）。

非目標（Non-goals，先不做）

  • 不重做/取代總部POS系統本身。
  • 不假設一開始就有POS API可寫入——先以「產出標準化資料（CSV/Excel/資料庫）」為主，POS串接視總部配合度而定。
  • 不處理付款、對帳、財務報表等延伸功能（MVP範圍外）。
  • 不支援供應商自行登入系統（單據來源仍是紙本）。

成功指標（暫定，待與店長確認）

  • 每日建檔時間從「手動輸入」大幅縮短（例如目標：每張單據辨識+覆核 < 1 分鐘）。
  • 品項/單價/數量辨識正確率達到「覆核微調即可」的水準（不需要整筆重打）。
  • 供應商單位換算 100% 依對照表正確換算（這塊不能靠OCR猜，需明確規則表）。

已知風險

  • 供應商單據格式不統一，且可能會變動（缺乏「一張範本走天下」的假設基礎）。
  • 手機拍照品質不穩定（光線、歪斜、皺褶紙張），影響辨識率。
  • 單位換算是「業務規則」而非影像辨識能解決的問題，容易被忽略但其實是專案的核心正確性風險。
  • 若最終要寫回POS，需視POS是否有可用的匯入/API管道，這點目前未知（待確認）。

02 · 影像辨識技術調查

拍照單據 → 結構化資料，這是整個專案技術難度最高的部分

方案分類

A. 傳統開源 OCR + 版面/表格辨識（自架、免費）

  • Tesseract 5.x / Tesseract.js：最成熟、社群最大的開源OCR引擎。安裝體積小（約10MB）、單頁辨識速度快（<1秒）、可在Node.js中透過 Tesseract.js 直接跑。但本身只做「文字辨識」，不含表格/版面結構化，中文準確率普通，需自己寫規則切欄位。
  • PaddleOCR（含 PP-StructureV3）：百度開源，針對中文/亞洲語系優化，內建 layout analysis 與表格結構辨識。缺點：主要是Python生態，體積較大，Node.js專案通常得包成獨立Python微服務。
  • RapidOCR：輕量化、模仿PaddleOCR效果但依賴更小，適合資源有限的環境。
  • Surya：對版面/多欄位文件辨識較強，但相對新、生態較小。

共同問題：這類方案辨識出來的是「文字＋位置」，仍需自己寫「版面解析規則」對應到「這一格是品項、那一格是單價」。5家供應商格式都不同，等於要為每家寫一套規則，格式微調就可能失效。屬於「開發/維護成本較高，但長期單張成本趨近於0」的路線。

B. 雲端 Document AI／表格辨識服務（付費）

  • Google Cloud Document AI：有Form Parser／Invoice Parser等預建處理器，也支援自訓練Custom Extractor。定價約每千頁US$1.5–30。
  • Azure AI Document Intelligence：預建Invoice/Receipt模型，也支援自訓練Custom Model；預建模型定價約每千頁US$10，自訓練後長期常比Google划算。
  • AWS Textract：AnalyzeExpense、表格擷取等功能，依功能不同每千頁約US$1.5–65。

對「標準發票/收據」效果好，但對「每家供應商自訂、非標準格式」的送貨單，通常仍需個別建立/訓練Custom Model，前期需蒐集每家供應商多張範例單據，導入門檻與工作量都不低。

C. 多模態 LLM Vision（拍照直接丟給大型視覺語言模型）

代表：Claude（Anthropic）、GPT-4o/GPT-5（OpenAI）、Gemini 2.5 Pro/Flash（Google）等，直接傳圖片＋prompt，模型直接回傳JSON，完全跳過傳統OCR pipeline。

  • 2026年行情：處理一頁單據約US$0.01–0.03，不需事先為每家供應商建樣板/訓練資料。
  • Gemini 2.5 Pro 在掃描/畫質較差文件上表現最好（約94%），Gemini Flash 2.0 適合高量重成本效益，GPT-4o適合需額外推理的複雜文件，Claude系列適合對幻覺風險容忍度低、需穩定輸出格式的流程。
  • Node.js生態已有現成模式：開源專案 zerox 把「丟圖給視覺模型、拿回結構化文字」包成一個函式呼叫。

不需訓練資料、不需為每家供應商寫死解析規則，格式變動也大多能自己適應（模型是「理解」而非「比對固定座標」），非常適合本案「格式不統一、單量不大」的情境。

建議

定案（2026-09-03）：往後固定沿兩條路線發展——主力是方案C LLM Vision（Claude）；備案／長期路線是方案A 開源自架（PaddleOCR/Tesseract+自寫規則）。方案B（雲端Document AI）不再列入規劃，詳見「10·API費用試算與備案」。
MVP 階段採用方案 C（LLM Vision API，例如 Claude API 的 vision 功能）。理由：本案單量小，API成本可忽略；5家供應商格式互異且可能變動，傳統OCR/自訓練模型的規則維護成本遠高於直接用LLM理解單據版面；開發時程最短，符合「總部沒資源、店長想先有可用工具」的實際需求；Node.js/Vue技術棧下，串接LLM Vision API只是一支REST呼叫，架構單純。

長期／量體擴大後：若擴散到多分店、單量大幅提升，可評估改用雲端Document AI自訓練Custom Model或PaddleOCR自架以降低長期單價成本，但這屬於後續優化。不論哪個階段，「單位換算表」都必須是明確維護的業務規則資料，不能期待任何辨識模型自己猜對。

04 · 系統架構提案（Node.js + Vue）

依技術人員指定的偏好，前端採 Vue、後端採 Node.js

整體流程

1
Vue 前端 — 拍照/上傳頁
上傳圖片 (multipart/form-data)
2
Node.js 後端 API
圖片預處理（裁切/壓縮/旋轉校正，可選）→ 呼叫 LLM Vision API（帶入固定JSON schema prompt）
3
LLM 回傳結構化 JSON
廠商猜測、品項陣列：[{品名, 單價, 數量, 原始單位}, ...]
4
後端套用「供應商對照表」
依供應商查詢單位換算規則，品名比對到店內標準品項代碼，換算成店內統一單位與價格
5
Vue 前端 — 覆核/修正頁
店長看到辨識結果表格，逐列確認/修改；標記新供應商/新品項時可即時建檔對照規則
6
店長按下「確認入帳」
Node.js後端寫入本地資料庫
7
匯出 CSV/Excel 給POS匯入
或未來：呼叫POS API寫入
辨識再準也會有錯（尤其單價、數量），因此設計上不做「自動直接入帳」，而是「辨識→預填→人工一鍵確認」，把AI當作「幫你把資料打好草稿」而非「幫你做決定」。即使辨識偶爾出錯，店長覆核一眼也能抓到，不會直接污染進出貨帳目。

資料模型（初版）

Vendor（供應商）
  - id
  - name（廠商名稱）
  - default_unit（該廠商慣用單位，如：台斤/公斤/箱，僅作預設值）
  - notes

VendorItemMapping（供應商品項對照/單位換算表）★核心業務規則表，非AI猜測
  - id
  - vendor_id
  - vendor_item_name（供應商單據上寫的品名，各廠商叫法可能不同）
  - store_item_id → StoreItem
  - unit_conversion_rate（供應商單位 → 店內標準單位換算率，例：1台斤 = 0.6公斤）
  - vendor_unit（來源單位）
  - store_unit（目標/店內標準單位）

StoreItem（店內標準品項主檔）
  - id
  - name（店內統一叫法，如：青江菜）
  - standard_unit（店內統一單位，如：公斤）
  - category（葉菜類/根莖類/肉品/滷包料...）

Receipt（單張進貨單記錄，對應一張拍照的紙本單）
  - id
  - vendor_id
  - photo_url（原始照片存檔路徑）
  - captured_at
  - status（辨識中/待覆核/已確認/已匯出）
  - raw_ocr_json（LLM原始回傳，供除錯/覆核比對用）

ReceiptLine（單據明細列，一張Receipt對多筆）
  - id
  - receipt_id
  - vendor_item_name_raw（辨識出的原始品名文字）
  - store_item_id（人工確認/系統比對後對應到的標準品項）
  - qty_raw / unit_raw（原始數量與單位）
  - qty_converted / unit_converted（換算後的店內單位數量）
  - unit_price（單價，注意：若供應商單位換算，單價也需對應換算）
  - confirmed（是否已人工確認）

辨識 Prompt / Schema 設計要點

  • 明確要求輸出固定JSON schema（例：vendor_name_guess, date_guess, items: [{name, qty, unit, unit_price}]），並在prompt中舉幾個真實單據範例（few-shot），提升穩定性。
  • 若辨識不確定（字跡模糊），要求模型明確標記 confidence: low 或留空，而不是硬猜——寧可讓店長補填，也不要讓模型「編造」看起來合理但錯誤的數字。
  • 建議先用少量真實單據照片做小規模測試（10~20張），評估辨識穩定度與常見錯誤類型，再決定是否加額外後處理規則。

單位換算：務必獨立於辨識邏輯

這是整個系統「正確性」最重要的一塊，且完全不該依賴辨識模型去猜換算率——換算規則要在 VendorItemMapping 表中由人工事先建好、店長可自行維護。辨識模型只需抓出「原始寫的數字與單位文字」，換算永遠由系統依規則表計算，確保帳目正確且可追溯來源。

部署建議（MVP）

  • 單店使用，資料量小：可先用一台小型雲主機（或店內電腦）跑Node.js + SQLite，不需複雜雲端架構。
  • 若之後考慮擴散到其他分店，再評估換成集中式後端（PostgreSQL + 多租戶資料模型，每店一個store_id）。

06 · 台灣送貨單格式模擬 + Vision Prompt / Schema 設計

還沒有真實供應商單據照片，先用模擬範例把辨識用的 prompt 與 schema 設計出來

Claude Max 訂閱額度不含 Anthropic API 用量，實際呼叫 Vision API 才會依用量計費（每張約US$0.01~0.015，見「成本試算」分頁）。這裡先把 prompt/schema/腳本骨架準備好、不執行，之後有真實單據照片或想正式測試時，再自備API key跑，或直接把照片丟給對話中的Claude做免費示範辨識。

台灣傳統食材送貨單常見格式特徵

  • 多為三聯式複寫單（存查聯／客戶聯／會計聯），複寫紙手寫，或半手寫半印刷。
  • 抬頭區：供應商名稱、（可能有）統一編號、地址電話、單據編號、日期；客戶欄為送達門市名稱。
  • 品項表格常見欄位：品名／規格／數量／單位／單價／金額／備註，但不是每家都齊全——小型菜商可能只有品名、數量、單價三欄，單位常手寫在數量旁而非獨立成欄（例：「青江菜 5台斤 @35」）。
  • 計價單位以「台斤」（1台斤=600克）為主，也可能是公斤、箱、包、尾（海鮮），且「台斤」與「市斤/公制斤」偶爾混用——這點必須靠供應商對照表鎖定，不能靠辨識模型自己判斷。
  • 單據下方常有供應商大小章及簽收欄，章可能蓋在品項表格上造成部分字跡被遮蓋。
  • 複寫紙字跡濃淡不一，手寫潦草，數字7與1、6與0容易混淆，是傳統OCR的痛點所在。

JSON Schema 設計

{
  "vendor_name_guess": "金*蔬果行",
  "receipt_no_guess": "0417",
  "date_guess": "2026-08-30",
  "items": [
    {
      "name_raw": "青江菜",
      "qty_raw": "5",
      "unit_raw": "台斤",
      "unit_price_raw": "35",
      "amount_raw": "175",
      "confidence": "high"
    },
    {
      "name_raw": "高麗菜",
      "qty_raw": "2",
      "unit_raw": "顆",
      "unit_price_raw": "45",
      "amount_raw": "90",
      "confidence": "medium"
    }
  ],
  "total_amount_on_receipt": "435",
  "notes": "部分品項被印章遮蓋，已標記為低信心"

設計原則：全部欄位保留「原始字面」（*_raw），不要求模型在這一步就換算單位或比對到店內品項代碼——這些交給後端 VendorItemMapping 規則表處理。每個品項附 confidence（high/medium/low），低信心欄位在覆核UI要用顏色標出來。total_amount_on_receipt 只作參考值，系統應自己加總 items[].amount_raw 並與此值比對，兩者對不上要提醒店長。

System Prompt 設計要點

你是一個食材送貨單辨識助手。請仔細觀察這張手寫/複寫紙送貨單照片，
盡量原樣抄錄單據上寫的文字與數字，不要自行換算單位、不要自行修正
看起來「合理」的數字。若某個欄位因為印章遮蓋、字跡模糊而無法確定，
仍要填入你最可能的判讀，但將該欄位的 confidence 標為 low，絕對不要
留空或用猜測值冒充高信心結果。輸出必須嚴格符合給定的 JSON schema，
不要加入額外文字說明。
  • 明確禁止模型「自己換算單位」——這是店家對照表的責任，不是辨識模型的責任。
  • 要求「原樣抄錄」而非「合理化修正」，避免模型把手寫潦草的數字自動腦補成看起來合理但錯誤的數字。
  • 要求嚴格JSON輸出，方便後端直接parse。
  • 拿到店長供應商真實單據後，把2~3張範例（含人工校正版辨識結果）放進prompt做few-shot，能顯著提升穩定度，尤其是辨識「這家供應商的字跡習慣」。

這類台灣手寫送貨單特有的OCR難點

  • 複寫紙字跡偏淡、部分區域幾乎看不清楚，需靠模型的上下文推理而非單純逐字辨識。
  • 「台斤」「斤」「公斤」「包」「箱」等單位常縮寫成一兩個字甚至用符號代替，同一供應商不同天寫法可能不一致。
  • 印章蓋在表格上是台灣單據常見情況，容易遮蓋數字，需要「低信心標記」機制而非要求100%辨識率。
  • 部分小型供應商純手寫、沒有印刷格線，表格結構要靠模型自己判斷「這一行對應哪些欄位」——這正是LLM Vision比傳統框線偵測型OCR（如img2table）更有優勢之處，但也代表萬一模型判斷錯換行對應關係，人工覆核這一步更不能省。

07 · 關鍵模組設計與可行性討論

還沒拿到真實單據範本、不急著寫程式，先把幾個決定「這個工具做不做得起來」的關鍵模組想清楚

模組一：品項比對與新品項建檔（Matching Engine）

供應商單據上寫的品名不會跟店內標準品項完全一樣——可能是「青江菜」vs 店內建的「青江菜(小)」，也可能潦草變成「菁江菜」，甚至同一供應商今天寫「大陸妹」明天寫「A菜」。這個比對沒做好，換算表就對不到，等於白做。

做法說明可行性評估
A. 純精確比對（baseline）品名字串完全相同才自動對應，對不上一律丟到「未對照」讓店長手動選實作最簡單，但初期未對照筆數會很多，覆核負擔重
B. 傳統模糊比對（編輯距離）用Levenshtein距離找最接近候選，列出前3名讓店長選能處理「青江菜/菁江菜」這類同音異字，但「大陸妹/A菜」這種完全不同字的同義詞抓不到
C. 讓LLM在辨識當下順便比對prompt裡附上店內標準品項清單，請模型辨識時直接標出最可能對應項，都不像則標記新品項建議做法不需額外開發比對引擎、不增加API呼叫次數，LLM對語意層級同義詞判斷能力遠優於編輯距離

建議：MVP直接採用C方案，把目前已知的店內標準品項清單（若在50~100項以內）放進system prompt。模型回傳時多帶一個 matched_store_item_id_guess 欄位，人工覆核只要確認/修正這個猜測即可。清單成長到上百種品項才需考慮向量檢索之類方案，以本案規模暫時不會遇到。

模組二：拍照品質守門（Photo Quality Gate）

手機拍照難免模糊、反光、拍到一半、光線太暗，這類照片辨識準確度會明顯下降，且浪費一次API呼叫與店長重拍等待的時間。

  • 前端簡易檢查：上傳前用瀏覽器原生 Canvas API 檢查解析度過低、檔案過小（可能過度壓縮或幾乎全白/全黑），成本為零。
  • 進階模糊偵測（拉普拉斯算子等）：技術可行，但MVP階段CP值不高。
  • 交給LLM自我回報：prompt要求模型若整張圖模糊到無法辨識大部分文字，回傳 photo_quality: "poor" 旗標，前端提示重拍，而不是硬辨識出一堆低信心錯誤資料。

建議：MVP採「前端簡易檢查（擋掉明顯太小/太暗的照片）＋讓LLM自我回報照片品質」的組合，不做進階影像處理。

模組三：信心度驅動的覆核流程

  • 低信心欄位要用明顯顏色/圖示標出，自動排到列表最上方或另開一區「請確認」。
  • 明細加總金額與單據上寫的合計金額對不上時，整張單據要有警示，不能默默放過。
  • 「未對照到店內品項」跟「已對照但信心低」要分開處理——前者一定要店長手動選/建，後者只是提醒覆核。

可行性：純前端邏輯與UI設計問題，不涉及額外技術風險。

模組四：匯出/POS串接的彈性設計（在還不知道POS規格的情況下）

目前完全不知道總部POS支不支援匯入、格式是什麼。在不知道目標格式的情況下，系統內部維護一份「自己的標準匯出格式」，不依賴任何特定POS：

日期, 供應商, 品項代碼, 品項名稱, 數量(店內單位), 單位, 單價, 金額, 備註

所有辨識、換算、覆核確認都是往這份內部標準格式寫資料，跟POS完全解耦。等之後確認POS實際規格（或有沒有API）後，只需另外寫一層「轉換器/adapter」，核心系統完全不用動。

可行性：標準adapter pattern，技術上沒有風險，重點是現在就把這個解耦的界線畫清楚，避免之後為配合某個POS格式把核心邏輯寫死。

模組五：供應商/單位換算規則維護介面

店長需要一個簡單畫面：新增/編輯供應商、新增/編輯「供應商品名→店內標準品項→換算率」對照規則、看到目前有哪些「未對照」品項待處理。

可行性：標準CRUD表單頁面，是MVP前端工作量估算裡最沒風險的一塊。

✅ 已實作（2026-09-03）：frontend/src/views/CatalogView.vue（路由/catalog），一頁三個tab整合「店內主檔／供應商／廠商對照表」。店內主檔跟對照表改成菜單式呈現——參考Uber Eats等電子點餐平台的UX：上方分類/供應商切換籤可篩選、卡片格取代單行列表、卡片右下角小圖示按鈕編輯/刪除。新增品項/供應商時代碼自動產生，避免打錯或衝突；對照表選店內品項一樣是下拉選單，不開放自由輸入；刪除有防呆（還被引用就擋掉並說明擋在哪幾筆）。已用Playwright驗證。

小結：目前設計是否站得住腳

上述五個模組合起來，整個系統的技術風險集中度其實很低——真正有不確定性的只有「LLM Vision辨識準確度到底夠不夠用」這一件事，這件事無法在沒有真實單據的情況下確認，其餘（比對、守門、覆核UI、匯出解耦、維護介面）都是常規工程工作。這也支持現在的判斷：等範本到手，先跑一次真實辨識驗證，比繼續往下設計更有意義——因為如果辨識準確度不夠，可能會回頭影響模組一（比對邏輯要不要更保守）跟模組三（覆核UI要不要更著重低信心提示）的設計，現在寫死反而可能要重改。

  6. 下一步：等更多天/更多供應商的單據累積，可以看出同一家供應商的格式穩定度，決定要不要幫每家供應商各自做few-shot範例；也建議之後拍照盡量正向、單頁、光線均勻。

廠商映射對照的實際發現

  1. 同一品項、多供應商採購的真實案例：「高麗菜」同時出現在雄泉鮮食（寫作「初秋高麗A*」）跟阿凱生蔬（寫作「高麗菜」），兩者都對應到店內同一個品項代碼V002。這正是「07·關鍵模組設計」模組一設計時設想的核心情境，現在有真實資料驗證，比對邏輯的價值直接被證實。
  2. 包裝規格 ≠ 單位換算，是另一個維度的問題：「黑豆干2斤/包」用「包」計價，但每包內容量是2斤——這不是台斤/公斤那種度量衡換算，而是「包裝規格」問題。若要做每台斤成本分析，需要額外的 pack_content_qty 欄位，跟單純的 conversion_rate 分開。已回頭補進「03·系統架構提案」的資料模型。
  3. 辨識信心與對照不確定性是分開的兩件事：阿凱生蔬單據「大陸妹韭菜」這一行，辨識信心是medium（字看得清楚），但對照上該算一筆還是拆成兩筆是不確定的——覆核UI不能只看辨識信心，還要有獨立的「比對不確定性」維度需要人工看過。
  4. 單位欄位文字跟備註欄位可能互相矛盾：玉米筍單位欄寫「盒」但品名備註「10包」；五香豆干單位欄寫「斤」但備註「2條」。這類衝突人靠常識能判斷，辨識模型未必能穩定處理，先標記待確認，不能讓系統自己猜。

一、Claude Vision API 實際收費怎麼算

Anthropic用「視覺token」計費，不是直接按張數收費。官方公式：

影像token數 = ⌈寬度px / 28⌉ × ⌈高度px / 28⌉
簡化估算：tokens ≈ (寬px × 高px) / 750

若圖片長邊超過1568px會先自動縮小再算，單張圖片最高約1568 tokens（標準畫質）——手機拍照解析度再高，實際計費的token數是有上限的。

今天（2026-09-02）Claude Sonnet 5 的開站優惠價已在8/31結束，目前正式牌價是 $3/M input、$15/M output；Haiku 4.5 維持 $1/M input、$5/M output。之前幾份文件殘留的優惠價估算數字會偏低，本頁數字才是目前準確的。

三、關於「本地訓練」的澄清

「本地訓練」有兩個不同概念需要分清楚：

  1. 自架（self-host）一個現成的開源模型：例如Qwen2.5-VL、MiniCPM-V，是別人已訓練好的公開權重，只是租一台有GPU的機器把它跑起來，不用自己訓練——上表「自架開源VLM」那一列在講的就是這件事。
  2. 從零訓練/微調自己的模型：需要蒐集大量標註資料（至少幾千張標註單據）、租用更貴的訓練用GPU叢集、花時間調參——本案規模（單店、15張/天）完全不划算，訓練成本會遠超過直接用API幾年的費用，且不保證品質更好。
不建議「訓練」，最多考慮「自架現成的開源模型」——而且以本案量體，連自架都不必要，直接用API的費用低到可以忽略（月成本US$0.4~6，比任何人的時薪都便宜太多）。
