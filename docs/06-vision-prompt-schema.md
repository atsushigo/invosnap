# 06. 台灣送貨單格式模擬 + Vision Prompt / Schema 設計

沒有真實供應商單據照片可用（等 [04-roadmap-open-questions.md](04-roadmap-open-questions.md) 的待確認事項3補齊），所以這份文件先根據台灣傳統市場/食材批發常見的「三聯式複寫送貨單」格式**模擬**一份範例，用來把辨識用的 prompt 與 JSON schema 設計出來、並列出這類單據常見的OCR難點。等真的拿到店長供應商的實際單據照片後，直接用它替換模擬範例做驗證即可，schema大方向應該不太需要大改。

## 台灣傳統食材送貨單常見格式特徵（調查所得）

- 多為**三聯式複寫單**（存查聯／客戶聯／會計聯），用複寫紙手寫，或半手寫半印刷的表格。
- 抬頭區：供應商名稱、（可能有）統一編號、地址電話、單據編號、日期。
- 客戶欄：送達門市名稱（本案即「川辣香＋分店」）。
- 品項表格：欄位通常是「品名／規格／數量／單位／單價／金額／備註」，但**不是每家都齊全**——小型菜商可能只有「品名、數量、單價」三欄，單位常常用手寫在數量旁邊而不是獨立成欄（例：「青江菜 5台斤 @35」）。
- 計價單位：傳統市場慣用「台斤」（1台斤=600克），但依供應商也可能用公斤、箱、包、尾（海鮮）、斤（要注意「台斤」與「市斤/公制斤」偶爾混用，需靠供應商對照表鎖定，不能靠辨識模型自己判斷）。
- 單據下方常有供應商**大小章（印章）**及簽收欄，章可能蓋在品項表格上造成部分字跡被遮蓋。
- 因為是複寫紙，字跡濃淡不一，且常見手寫潦草、數字7與1、6與0容易混淆等傳統OCR痛點。

## 模擬範例單據（非真實廠商資料，僅供設計參考）

```
┌───────────────────────────────────────────────┐
│  金*蔬果行                        送貨單編號: 0417 │
│  電話: 04-xxxx-xxxx                日期: 2026/08/30 │
│  客戶: 川辣香 OO店                                  │
├───────────────────────────────────────────────┤
│ 品名        │ 數量   │ 單位 │ 單價  │ 金額     │
├───────────────────────────────────────────────┤
│ 青江菜       │  5     │ 台斤 │  35   │  175    │
│ 小白菜       │  3     │ 台斤 │  30   │  90     │
│ 高麗菜       │  2     │ 顆   │  45   │  90     │
│ 豆芽         │  4     │ 台斤 │  20   │  80     │
├───────────────────────────────────────────────┤
│                              合計:  435          │
│                         [廠商章戳，部分蓋在表格邊緣]│
└───────────────────────────────────────────────┘
（手寫字跡、複寫紙偏淡、部分數字被印章邊緣壓到）
```

這份模擬單刻意包含幾個「真實情境會遇到」的雜訊：字跡而非印刷體、單位手寫在數量欄內、印章壓到表格邊緣、合計欄位可能和明細加總對不上（人工手寫易算錯，系統應該用明細加總為準、不要直接信合計數字）。

## JSON Schema 設計

要求 LLM Vision 固定輸出以下結構，欄位盡量貼近「原始單據上寫的東西」，換算與比對留給後端規則處理，不要求模型做業務判斷：

```json
{
  "vendor_name_guess": "金*蔬果行",
  "receipt_no_guess": "0417",
  "date_guess": "2026-08-30",
  "items": [
    {
      "name_raw": "青江菜",
      "qty_raw": "5",
      "unit_raw": "台斤",
      "unit_price_raw": "35",
      "amount_raw": "175",
      "confidence": "high"
    },
    {
      "name_raw": "高麗菜",
      "qty_raw": "2",
      "unit_raw": "顆",
      "unit_price_raw": "45",
      "amount_raw": "90",
      "confidence": "medium"
    }
  ],
  "total_amount_on_receipt": "435",
  "notes": "部分品項被印章遮蓋，已標記為低信心"
}
```

欄位設計原則：
- 全部欄位保留「原始字面」（`*_raw`），不要求模型在這一步就換算單位或比對到店內品項代碼——這些交給後端 `VendorItemMapping` 規則表處理（見 [03-architecture-proposal.md](03-architecture-proposal.md)）。
- 每個品項要求附 `confidence`（high/medium/low），低信心的欄位在覆核UI要用顏色標出來，提示店長優先檢查。
- `total_amount_on_receipt` 只作為「比對用」的參考值——系統應該自己加總 `items[].amount_raw` 並與此值比較，兩者對不上時要提醒店長（常見於手寫單合計算錯，或某品項被遮蓋沒抓到）。

## System Prompt 設計要點

```
你是一個食材送貨單辨識助手。請仔細觀察這張手寫/複寫紙送貨單照片，
盡量原樣抄錄單據上寫的文字與數字，不要自行換算單位、不要自行修正
看起來「合理」的數字。若某個欄位因為印章遮蓋、字跡模糊而無法確定，
仍要填入你最可能的判讀，但將該欄位的 confidence 標為 low，絕對不要
留空或用猜測值冒充高信心結果。輸出必須嚴格符合給定的 JSON schema，
不要加入額外文字說明。
```

要點：
- 明確禁止模型「自己換算單位」——這是店家對照表的責任，不是辨識模型的責任。
- 明確要求「原樣抄錄」而非「合理化修正」，避免模型把手寫潦草的數字自動「腦補」成看起來合理但其實錯誤的數字。
- 要求嚴格JSON輸出，方便後端直接parse，不需要額外處理自然語言包裝。
- 建議之後拿到店長供應商真實單據後，把2~3張範例（含辨識結果人工校正版）放進prompt做few-shot，能顯著提升穩定度，尤其是辨識「這家supplier的字跡習慣」。

## 這類台灣手寫送貨單特有的OCR難點（給後續測試時參考）

- 複寫紙字跡偏淡、部分區域幾乎看不清楚，需靠模型的「上下文推理」而非單純逐字辨識。
- 「台斤」「斤」「公斤」「包」「箱」等單位常常縮寫成一兩個字甚至用符號代替，同一供應商可能不同天寫法不一致。
- 印章蓋在表格上是台灣單據常見情況，容易遮蓋數字，需要有「低信心標記」機制而非要求100%辨識率。
- 部分小型供應商是純手寫、沒有印刷格線，表格結構要靠模型自己判斷「這一行對應哪些欄位」，這正是LLM Vision（理解型）比傳統框線偵測型OCR（如img2table）更有優勢的地方——但也代表萬一模型判斷錯「換行對應關係」，人工覆核這一步更不能省。
