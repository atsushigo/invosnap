# 07. 關鍵模組設計與可行性討論

在還沒拿到真實單據範本、還不急著寫程式的階段，先把幾個決定「這個工具做不做得起來」的關鍵模組想清楚，逐一討論可行性與設計選項。目標是：等範本一到手，這些設計決策已經想過一輪，不用臨場現想。

## 模組一：品項比對與新品項建檔（Matching Engine）

**問題**：供應商單據上寫的品名不會跟店內標準品項完全一樣——可能是「青江菜」vs 店內建的「青江菜(小)」，也可能供應商手寫潦草變成「菁江菜」，甚至同一供應商今天寫「大陸妹」明天寫「A菜」。這個比對沒做好，換算表就對不到，等於白做。

**方案選項**：

| 做法 | 說明 | 可行性評估 |
|---|---|---|
| A. 純精確比對（baseline） | 品名字串完全相同才自動對應，對不上一律丟到「未對照」讓店長手動選 | 實作最簡單，但初期未對照筆數會很多，店長覆核負擔重 |
| B. 傳統模糊比對（編輯距離/字串相似度） | 用 Levenshtein距離或類似演算法，在店內品項清單中找最接近的候選，列出前3名讓店長選 | 需要額外寫比對邏輯與門檻調校，中文同音異字（青江菜/菁江菜）這類編輯距離法可以處理，但「大陸妹/A菜」這種完全不同字但同義的狀況抓不到 |
| C. 讓LLM在辨識當下順便比對 | 在丟給Vision API的prompt裡，附上店內目前的標準品項清單，請模型辨識時直接標出「最可能對應到清單中的哪一項，若都不像則標記為新品項」 | **建議做法**。不需要額外開發比對引擎、不增加API呼叫次數（同一次呼叫順便做），LLM本身對「大陸妹＝A菜」這類語意層級的同義詞判斷能力遠優於編輯距離演算法 |

**建議**：MVP直接採用C方案，把「目前已知的店內標準品項清單」放進system prompt裡（品項數量若不多，如50~100項以內，塞進prompt完全沒問題）。模型回傳時除了原始品名，多回傳一個 `matched_store_item_id_guess`（可能為null）欄位，人工覆核時只要確認/修正這個猜測即可，比店長自己從落落長清單裡選好選很多。清單成長到很大（例如上百種品項）時才需要考慮換成向量檢索之類的方案，但以本案5家供應商、每天約15張單據的規模，暫時不會遇到這個問題。

> **真實單據驗證後更新（2026-09-02，見 [08-real-receipt-samples.md](08-real-receipt-samples.md)）**：拿到的真實單據裡，至少一家供應商在單據上就印有自己的**品項編號**（如 B0002、D0007-1），不是每家都只能靠品名比對。比對優先序應調整為：① 若單據有供應商品項編號，優先用「（供應商ID, 供應商品項編號）→ 店內標準品項」精確比對（這比任何模糊比對都可靠）；② 沒有品項編號的單據（多數生鮮/手寫單），才退回用C方案的LLM語意比對。`VendorItemMapping` 資料表（見 [03](03-architecture-proposal.md)）應該加一個可為null的 `vendor_item_code` 欄位來支援這個優先序。

## 模組二：拍照品質守門（Photo Quality Gate）

**問題**：手機拍照難免會有模糊、反光、只拍到一半、光線太暗等狀況，這類照片丟給模型辨識準確度會明顯下降，且浪費一次API呼叫（雖然單價低，但浪費店長的時間更關鍵——辨識完才發現照片不能用，等於要重拍+重等）。

**方案選項**：

- **前端簡易檢查**（拍照/選圖後，上傳前先做）：檢查圖片解析度是否過低（例如小於某個像素門檻）、圖片檔案是否過小（可能代表過度壓縮或幾乎全白/全黑）。這些用瀏覽器原生 Canvas API 就能做，不需要額外函式庫，成本是零。
- **進階模糊偵測**（例如拉普拉斯算子/影像銳利度分析）：技術上可行，但需要額外的影像處理邏輯或函式庫，對MVP階段的CP值不高。
- **交給LLM自己判斷**：在prompt裡要求模型如果「整張圖片模糊到無法辨識大部分文字」，直接回傳一個 `photo_quality: "poor"` 的旗標，前端看到這個旗標就提示店長重拍，而不是硬辨識出一堆低信心的錯誤資料。

**建議**：MVP採「前端簡易檢查（擋掉明顯太小/太暗的照片）＋讓LLM自我回報照片品質」的組合，不做進階影像處理。這樣多數「拍壞了」的情況能在源頭被擋掉或提早發現，不需要額外開發成本。

## 模組三：信心度驅動的覆核流程

**設計要點**：覆核頁不是把辨識結果平鋪直敘列出來，而是要讓店長的眼睛第一時間就落在「該注意的地方」：

- 低信心（`confidence: low`）的欄位要用明顯的顏色/圖示標出來，並自動排到列表最上方或另外一區「請確認」。
- 明細加總金額 與 單據上寫的合計金額 對不上時，整張單據要有一個警示，而不是默默放過。
- 「未對照到店內品項」的列要跟「已對照但信心低」的列分開處理——前者一定要店長手動選/建，後者只是提醒覆核。

**可行性**：純前端邏輯與UI設計問題，不涉及額外技術風險，只要在寫覆核頁UI時把這個排序/分類邏輯設計進去即可。

## 模組四：匯出/POS串接的彈性設計（在還不知道POS規格的情況下）

**問題**：目前完全不知道總部POS支不支援匯入、格式是什麼（見 [04-roadmap-open-questions.md](04-roadmap-open-questions.md) 待確認事項1）。在不知道目標格式的情況下，要怎麼設計才不會等資訊確認後要整套重寫？

**設計方案**：系統內部維護一份「自己的標準匯出格式」（不依賴任何特定POS），例如：

```
日期, 供應商, 品項代碼, 品項名稱, 數量(店內單位), 單位, 單價, 金額, 備註
```

所有的辨識、換算、覆核確認都是在往這份**內部標準格式**寫資料，跟POS完全解耦。等之後確認POS的實際匯入規格（或有沒有API）後，只需要另外寫一層「轉換器/adapter」，把內部標準格式轉成POS要的格式，核心系統（拍照、辨識、換算、覆核）完全不用動。

**可行性**：這是標準的adapter pattern，技術上沒有風險，重點只是「現在就把這個解耦的界線畫清楚」，避免之後為了配合某個POS格式把核心邏輯寫死。

## 模組五：供應商/單位換算規則維護介面

**設計要點**：店長需要一個簡單的畫面（不必花俏），可以：
- 新增/編輯供應商（名稱、預設單位）
- 新增/編輯「供應商品名 → 店內標準品項 → 換算率」的對照規則
- 看到目前有哪些「未對照」的品項待處理

**可行性**：就是一個標準CRUD表單頁面，技術上沒有難度，是MVP前端工作量估算裡最沒風險的一塊。

## 小結：目前設計是否站得住腳

上述五個模組合起來，整個系統的技術風險集中度其實很低——真正有不確定性的只有「LLM Vision辨識準確度到底夠不夈用」這一件事，這件事無法在沒有真實單據的情況下確認，其餘（比對、守門、覆核UI、匯出解耦、維護介面）都是常規工程工作，沒有特別的技術瓶頸。這也支持你現在的判斷：**等範本到手，先跑一次真實辨識驗證，比繼續往下設計更有意義**——因為如果辨識準確度不夠，可能會回頭影響模組一（比對邏輯要不要更保守）跟模組三（覆核UI要不要更著重低信心提示）的設計，現在寫死反而可能要重改。
