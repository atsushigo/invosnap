# 05. 成本試算、開源方案與台灣市場參考

補充 [02-ocr-tech-research.md](02-ocr-tech-research.md) 的技術路線比較，這份文件聚焦在「實際要花多少錢」以及「有沒有現成的開源/商業方案可以直接參考、甚至不用自己做」。

## 一、成本試算（以本案單量：約15張/天、450張/月 估算）

| 方案 | 單頁成本 | 月成本估算（450張） | 一次性成本 | 備註 |
|---|---|---|---|---|
| **LLM Vision API — Claude（建議方案）** | 約US$0.01～0.015/張（依圖片解析度與輸出JSON長度） | 約US$4.5～7 | 幾乎無（不需訓練/標註資料） | 依token計費：一張單據圖片約1,000~1,600 tokens + 少量文字prompt，回傳JSON約幾百tokens |
| LLM Vision API — GPT-4o | 約US$0.01～0.03/張 | 約US$4.5～13.5 | 無 | 適合需要較強推理判斷模糊欄位時 |
| LLM Vision API — Gemini Flash | 約US$0.001～0.005/張（最低價位） | 約US$0.5～2.3 | 無 | 高量、重成本效益時的替代選項 |
| 雲端 Document AI — Google/Azure/AWS（用預建通用模型） | 約US$0.0015～0.03/張（每千頁US$1.5～30） | 約US$0.7～13.5 | 低（不訓練） | 對非標準格式單據辨識效果通常不如客製模型 |
| 雲端 Document AI（訓練Custom Model，每家供應商各一個樣板） | 同上 API 費 | 同上 | **中～高**：需蒐集每家供應商10~50張範例單據標註、上傳訓練、反覆調整 | 5家供應商 = 至少5套模型要維護，格式一變就要重訓 |
| 開源自架 — PaddleOCR / Tesseract + 自寫解析規則 | US$0（僅主機電費/算力） | 主機成本（若本來就有電腦/NAS可跑，約US$0~5/月） | **高**：工程師要為每家供應商寫版面解析規則、除錯 | 長期單價最低，但前期人力投入最高，格式微調就要改規則 |

**結論**：以本案「15張/天」這種小單量而言，任何方案的**API費用本身都不是重點**（每月頂多十幾美元），真正決定成本的是**前期開發/維運人力**。這也是為什麼 [02](02-ocr-tech-research.md) 建議MVP直接用LLM Vision API——省下的是「為5家供應商各寫一套規則/各訓練一個模型」的工程時間，而不是省API費用本身。

> 註：以上為2026年8月公開資料的粗估區間，實際費率請在導入前以官方最新定價頁面為準（模型與定價會持續更新）。

## 二、開源 GitHub 專案參考

### A. 可直接拿來用/參考架構的「文件理解」模型

| 專案 | 說明 | 適用性 |
|---|---|---|
| [clovaai/donut](https://github.com/clovaai/donut) | OCR-free 文件理解 Transformer，圖片直接輸出結構化 JSON，不需另外接 OCR 引擎，ECCV 2022 論文的官方實作 | 概念上與「LLM Vision直接輸出JSON」的思路相同，但donut是要「自己拿資料微調(fine-tune)」的模型，不是open API，適合未來想做到「完全離線、不依賴外部API」時參考 |
| [philschmid/document-ai-transformers](https://github.com/philschmid/document-ai-transformers) | Hugging Face 生態下 LayoutLM/Donut 等文件AI模型的微調範例 | 學習如何用自己的單據資料微調模型的參考教材 |
| Table Transformer (TATR，微軟) | 基於Transformer的表格偵測與結構重建模型，搭配 PubTables-1M 資料集 | 若之後想強化「表格框線抓取」精準度可參考，屬於研究型專案，導入需要一定ML工程能量 |
| [fahmiaziz98/receipt_parsing](https://github.com/fahmiaziz98/receipt_parsing) | 用 Donut 模型做收據解析的實作範例，作者也提到後續會加入 LLM/VLM 方案 | 小型範例專案，可看架構思路，不建議直接商用 |

### B. 可直接整合進 Node.js/Python pipeline 的實用工具庫

| 專案 | 說明 |
|---|---|
| [Tesseract.js](https://github.com/naptha/tesseract.js) | 純JS/Node可直接跑的Tesseract封裝，若要完全不依賴Python服務、想在Node裡就地跑OCR，這是最直接的選擇（但如前述，中文表格辨識能力有限） |
| PaddleOCR（百度官方 GitHub） | 中文/表格辨識能力較強，Python生態，需包成獨立微服務讓Node呼叫 |
| [img2table](https://github.com/xavctn/img2table)（Python） | 專門做「表格框線偵測＋內容擷取」，可搭配 Tesseract/PaddleOCR 當文字辨識引擎，能直接輸出成Excel、保留原始表格結構，是「規則式表格抓取＋OCR」組合中很成熟的一個庫，值得列入自架方案的優先評估對象 |
| [zerox](https://github.com/getomni-ai/zerox)（Node.js/TypeScript） | 把「丟圖給視覺語言模型、拿回結構化文字」包成一個函式呼叫，概念與本案MVP走LLM Vision的方向一致，可直接參考其prompt設計與呼叫方式，甚至直接拿來當雛型的起點 |

### C. 資料集（若未來要自己訓練/微調模型時參考）

- **SROIE**：1000張掃描收據資料集，含OCR標註，收據辨識研究常用基準。
- **CORD**：常搭配 Donut/LayoutLM 使用的收據資料集。
- 這些是「英文/其他語系收據」為主的公開資料集，不含台灣供應商的中文送貨單格式，若走「自訓練模型」路線，最終仍需要自己蒐集、標註店長實際收到的單據，公開資料集只能當作起步練習用。

## 三、台灣本地 POS／零售科技廠商概況（找有沒有現成方案可以直接買/串接）

調查目的：與其自己做，是否已有台灣廠商做過「拍照建檔進貨單」這類功能，可以直接採購或串接，省去自建的必要。

> 更新（深查後修正）：瑞乘科技的「AI影像辨識」經查證是商品條碼/自助結帳辨識，**與進貨單辨識無關**（先前誤把另一家「瑞艾科技 iSeek」的14種AI影像辨識服務混入瑞乘科技，已修正）。深查也找到一家**明確做同類功能的競品 FOODIVAL**，詳見下表與結論。

| 廠商/服務 | 相關性 | 說明 |
|---|---|---|
| **★ FOODIVAL（foodival-procurement.com）** | <span style="font-weight:600">高——直接命中</span> | 明確主打「餐廳前線員工用手機拍攝收貨單，AI自動識別食材名稱/數量/價格」，功能與InvoSnap設計**完全一致**。客戶為香港大中型連鎖餐飲（如但馬屋火鍋），未見明確服務台灣市場的資訊，定價未公開，中文手寫辨識支援度不明。聯絡方式：foodival@flexsystem.com |
| **力新國際 NewSoft** | 中 | 有明確API/單機版產品「企業單據憑證辨識」，內建90萬筆廠商資料庫、支援手寫辨識，單機版每月不到千元，也有API可整合ERP，並提供免費試用。是台灣本地最接近的商用OCR方案，但服務定位是企業報支憑證（發票/收據），非餐飲進貨單場景，需洽詢是否可客製 |
| **瑞乘科技（RIX，代理銀豹 POSPAL 等）** | 低（已修正） | 官網服務項目/產品頁確認其「自動報貨」是連鎖零售/餐飲的補貨/叫貨管理，AI影像辨識指的是「手機商品掃描結帳」，**沒有**進貨單/發票辨識功能，與本案需求不符 |
| **群豐資訊** | 低～中 | 提供餐飲營運管理POS，含採購決策、庫存管理，但公開資訊未特別提及「拍照辨識供應商送貨單」此類自動化功能 |
| 王品、瓦城等大型餐飲集團 | 參考 | 已導入進銷存/成本管理系統，顯示「原料進貨數位化」在台灣餐飲業是有前例的既有需求，但這些多為大型集團自建/客製系統，非中小型連鎖可直接取用的現成產品 |
| 校園食材登錄平台 / 綠界・ezPay電子發票 | 不相關 | 前者是政府溯源用途、非商用；後者僅是電子發票開立API，沒有OCR辨識供應商單據的功能，順帶排除 |

**結論（深查後更新）**：
1. **FOODIVAL 的存在證明這個利基需求已經被市場驗證過**——至少在香港，已經有廠商把「拍收貨單→AI辨識食材品項/數量/價格」做成商用產品賣給連鎖餐飲。這代表InvoSnap想做的方向是對的，不是憑空想像的偽需求。
2. 但**目前沒有查到它明確服務台灣市場**，中文手寫（尤其台灣傳統市場的複寫紙送貨單）支援度也不明，值得直接寄信詢問（foodival@flexsystem.com）是否服務台灣、報價、以及對台式手寫單據的辨識能力。
3. 力新國際的次要建議是可以問問是否能客製化到餐飲進貨單場景，畢竟他們已經有現成的OCR辨識引擎與90萬筆廠商資料庫基礎。
4. 瑞乘科技可以降低優先度，目前產品線沒有對應功能，不用花時間深談。
5. 如果洽詢後確認沒有台灣本地可直接採購的現成方案，那自建InvoSnap的價值就更明確——甚至長期有機會往「做成產品賣給其他台灣中小型連鎖餐飲」的方向發展（FOODIVAL在香港的存在也證明這個市場有付費意願）。
